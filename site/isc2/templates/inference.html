Challenge

  • One GPU host (NVIDIA GB10), one large Qwen model, several teams sending requests at the same time
  • Find the concurrency where throughput stops growing and latency starts to hurt
  • Know when the KV cache, not compute, becomes the limit

Solution

  • vLLM serving qwen38-lil, at most 16 sequences in parallel
  • Load generator in the console: fixed prompt set, 30 s runs, concurrency 1, 2, 4, 8, 16
  • vLLM metrics (num_requests_running, num_requests_waiting, kv_cache_usage_perc) scraped by Prometheus and copied into every run timeline

Trade-offs

  • Concurrency 16: {{tr_x}} throughput, paid with {{tr_ttft}} time to first token p95
  • GPU utilization stays at {{gpu_min}}–{{gpu_max}} % in every run: it cannot tell 1 request from 16
  • 30 s runs on a shared host: one run per setting, no confidence interval

What I'd change at scale

  • Second replica and prefix-aware routing (llm-d or the vLLM router) once a second GPU exists
  • Speculative decoding, measured with the same console runs (the KV cache is already FP8)
  • Admission control on queue length instead of a fixed 16-slot limit
