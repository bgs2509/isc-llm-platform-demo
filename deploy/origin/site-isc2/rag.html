Ask the agent

Question:

Challenge

  • Answer questions about the client firm's public blog with the source article
  • Answer questions about the running platform from live data, not from the model's memory
  • Prove the quality with numbers, re-run after every change

Solution

  • Corpus: 36 blog articles, chunked by text kind (whole case study, by section, or paragraph windows)
  • Retrieval: BM25, standard library only; every chunk starts with its title and URL
  • Agent: the model picks tools through OpenAI tools; at most 3 rounds; temperature 0
  • Tools: search_docs(query), platform_status(view) (alerts or teams from Prometheus; the model never writes PromQL)
  • Calls go through the gateway with a team key: agent tokens and spend are accounted like any team's

B6 · How was run-to-run variability handled when running large jobs on IonQ quantum hardware through Braket?hit8.4 s
First tool: search_docsSources cited: Conquering the Noise: How We Overcame Variability in Large-Scale Runs of Braket’s IonQ ServiceClaims supported: 18 of 18Answer: They handled it with a "litmus test" for noise consistency: - **The problem:** Large circuit batches (40–50+ circuits) on Braket's IonQ service get split into separate batch runs ("execution windows") executed sequentially throughout the day, with no control over ordering. Results were consistent within a batch but inconsistent across batches, since the noise profile can shift drastically between windows and drift over time. - **The approach:** They designed a two-qubit litmus circuit of six alternating CNOT gates, decomposed into 24 subcircuits (4 inputs × 1–6 CNOTs). After running the batch, they (1) estimated the average error probability per CNOT gate across all 24 circuits, and (2) computed the variance of the errors and compared it against a tolerance value. - **The decision rule:** If the variance exceeded tolerance, the noise profile was deemed too inconsistent to trust the payload batch — and execution was terminated immediately, saving the client money. - **Next steps:** They planned to embed the litmus test into routine batch execution, mixing random litmus circuits into payload batches to verify noise consistency and use the results to compare batches and adjust for drift.
B7 · How can someone put a dollar figure on the value an open source project creates?hit10.1 s
First tool: search_docsSources cited: Measuring the value of open source, part two: actually having the conversation, Measuring the Value of Open Source, Part One: Coming Up With Some NumbersClaims supported: 16 of 16Answer: Based on the blog posts, here's how to put a dollar figure on the value an open source project creates: **Core method: work backwards from project revenue** - Dig in with product teams to find out how much time/money the open source effort saved or generated for them. - Interview project leaders (e.g., 12+ leaders who received open source support over the past year). - Attribute a percentage of the project's success to the open source contribution (in their case, 2–25%). Example: a $100M project with 10% attribution = $10M in value generated. - **Round down / be conservative** — e.g., cut an estimate by two-thirds to get a defensible floor (their example dropped to ~$270K for a single fix). - **Validate the numbers with Finance** for credibility. **Key principles** - The goal isn't an exact number — it's having the conversation with stakeholders and establishing that the contribution is non-zero (and likely much more). - Aggregate many small wins: even conservative estimates of individual fixes/improvements add up quickly over a year. - Expect the real financials to be hard to obtain; you'll need allies, since many companies obscure project costs and revenue. **Why it matters** - Positioning the open source program as a value generator (rather than a cost center) makes its budget defensible and builds executive buy-in over time. Note: this process is time-intensive — their example took 10–12 managers and 2–3 months of conversations for a single department head.

B10 · What are the usual reasons that data science projects do not deliver?hit7.5 s
First tool: search_docsSources cited: Why Data Science FailsClaims supported: 26 of 26Answer: According to the blog post "Why Data Science Fails" (insightsoftmax.com), the usual reasons data science projects don't deliver include: 1. **Starting with the tool, not the problem** — fitting a problem to a trendy tool (e.g., using an LLM just because it's hyped) instead of choosing the right tool for the problem. 2. **Using fancy tools on simple problems** — e.g., throwing a neural network at something a linear regression would solve, wasting money. 3. **Poor data quality** — "garbage in, garbage out"; bad or inaccessible data yields misleading or wrong answers. 4. **The solution goes unused** — end users aren't trained, processes never adapt, or users don't even know the feature exists. 5. **Company culture disincentivizes use** — bonus structures reward the old method, or users fear the tool will make them redundant. 6. **No end-to-end view** — ignoring the software engineering needed to put the solution into production for real users. 7. **Business problem and outcomes not defined** — skipping proper problem definition and specification before building. Trade-offs

  • BM25 instead of embeddings: no new service and no second model in GPU memory; no synonyms
  • The judge is the model under test; questions written by us from the corpus
  • 16 questions: enough to catch a regression, too few for a confidence interval

What I'd change at scale

  • Dense retrieval through an embedding model behind the same gateway (vLLM pooling runner)
  • A judge from a different model family; questions from real user logs
  • Evaluation in CI: block a release when hit@3 or faithfulness drops
