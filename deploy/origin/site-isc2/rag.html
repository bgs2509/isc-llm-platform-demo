Question:

Challenge

  • Answer questions about the client firm's public blog with the source article
  • Answer questions about the running platform from live data, not from the model's memory
  • Prove the quality with numbers, re-run after every change

Solution

  • Corpus: 36 blog articles, chunked by text kind (whole case study, by section, or paragraph windows)
  • Retrieval: BM25, standard library only; every chunk starts with its title and URL
  • Agent: the model picks tools through OpenAI tools; at most 3 rounds; temperature 0
  • Tools: search_docs(query), platform_status(view) (alerts or teams from Prometheus; the model never writes PromQL)
  • Calls go through the gateway with a team key: agent tokens and spend are accounted like any team's

B6 · How was run-to-run variability handled when running large jobs on IonQ quantum hardware through Braket?hit8.6 s
First tool: search_docsSources cited: Conquering the Noise: How We Overcame Variability in Large-Scale Runs of Braket’s IonQ ServiceClaims supported: 19 of 19Answer: They handled it with a "litmus test" for noise-profile consistency: - **The problem:** Large circuit batches (>40–50 circuits) on Braket's IonQ service get split into separate "execution windows" throughout the day, with no control over ordering. Results were consistent within a batch but inconsistent across batches, since the noise profile shifts drastically between windows and drifts over time. - **The test:** They built a 2-qubit circuit of six alternating CNOT gates and decomposed it into 24 subcircuits (4 inputs × 1–6 CNOTs). If the batch shares a consistent noise profile, the data should look a certain way; outliers reveal inconsistency. - **The decision rule:** After execution, they estimate the average error probability per CNOT gate across all 24 circuits and compute the variance of errors. If variance exceeds a tolerance, the noise profile is deemed untrustworthy and the payload batch execution is terminated early — saving the client money. - **Next steps:** Incorporate the litmus test into routine execution, sprinkle random circuits from the 24-circuit batch into payload batches to verify consistency, and use the tests to compare batches and adjust for drift.

First tool: search_docsSources cited: Why Data Science FailsClaims supported: 27 of 27Answer: According to the blog post "Why Data Science Fails," the usual reasons data science projects don't deliver include: 1. **Starting with the tool, not the problem** — fitting a problem to a trendy tool (e.g., using an LLM just because it's hyped) instead of choosing the right tool for the problem. 2. **Using fancy tools on simple problems** — e.g., throwing a neural network at something a simple regression would solve, wasting money. 3. **Poor data quality** — "garbage in, garbage out"; bad or inaccessible data yields no value, or worse, misleading answers that look correct. 4. **The solution goes unused** — end users aren't trained, company processes never adapt, or users don't even know the feature exists. 5. **Company culture disincentivizes adoption** — bonus structures reward the old method, or users fear the new tool will make them redundant. 6. **No end-to-end view** — treating the solution in isolation without the software development needed to put it into production. 7. **Business problem and outcomes not thought through** — skipping proper problem definition and specification before building. Trade-offs

  • BM25 instead of embeddings: no new service and no second model in GPU memory; no synonyms
  • The judge is the model under test; questions written by us from the corpus
  • 16 questions: enough to catch a regression, too few for a confidence interval

What I'd change at scale

  • Dense retrieval through an embedding model behind the same gateway (vLLM pooling runner)
  • A judge from a different model family; questions from real user logs
  • Evaluation in CI: block a release when hit@3 or faithfulness drops
